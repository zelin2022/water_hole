# In-game feedback

The v0.1.24 receiver is deployed behind Cloudflare Tunnel at `https://waterhole-feedback.epsiloneridanigames.com`. HTTPS, the tunnel, localhost-only listeners, service resource limits, server-validated Turnstile reporting, and public visitor-IP rate limiting have been verified. Submissions are enabled for controlled live checks; the game build's online endpoint is not configured yet. Live survey verification, the edge rate rule, and native packaged-game testing remain pending. Turnstile credentials are configured privately; SSH credentials and deployment-specific server addresses are not stored in this repository.

## Player experience

Press **F8** during an expedition to pause and report a bug. This action is rebindable in Settings. Capture only the game canvas, downscaled to fit 1280 × 800 pixels, as a PNG up to 1 MiB. Show the image before submission and let the player remove it. There is no file picker or custom image-upload control. Reports include editable text and the existing reproducible game details. Capture or storage failures leave text reporting and local exports available.

The ending congratulates the player on beating the demo and offers an optional one-to-five-star rating and suggestions. The survey has no screenshot attachment. It does not resume the completed expedition. The developer panel's **Warp to demo end** transfers existing water into the completed-run ledger, preserving water and credits, then opens this ending for testing. Public release builds remove the warp control with the other developer tools.

Drafts stay locally until the player chooses Send. A configured build asks for a human check in a separate hosted verification frame, then sends the selected report or survey. Failed requests keep the draft. Repeating the same submission uses its existing UUID; changing its content creates a new UUID. Copy/download alternatives remain available while online reporting is unconfigured.

## Request path

```text
Game report or survey
  -> verification iframe on the configured HTTPS origin
  -> server-validated Turnstile token
  -> POST /api/reports or POST /api/surveys
  -> private, bounded SQLite inbox
```

Set `VITE_FEEDBACK_API_URL` to the HTTPS service origin when rebuilding the client. Build-time CSP grants network/frame access only to that configured origin. The game validates the verification frame's exact window, origin, request nonce and action before accepting its token. No shared secret is embedded in the game. The provider secret stays on the receiver; its server checks hostname, action, token age and verification success.

See [receiver configuration, API, limits and private inbox commands](../feedback-server/README.md). `npm test` includes receiver tests; Node.js 24 is required for the built-in SQLite runtime. `npm run feedback:start` starts the receiver on loopback with submissions disabled unless explicitly enabled and fully configured. It does not publish a port or configure infrastructure.

## Hosting decision

The available instance is an active VPN/home-access gateway with a small memory budget. Feedback uses separate unprivileged services with bounded CPU/memory and private storage, preserving the existing VPN containers, networks, SSH, Tailscale, and public listeners.

The selected route is **Cloudflare Tunnel**, with public origin **`https://waterhole-feedback.epsiloneridanigames.com`**. The registered domain uses Cloudflare nameservers. The hostname is a single subdomain label, covered by ordinary Universal SSL. The account owner registered the tunnel and Turnstile widget, ran the reviewed installer, and published the hostname to the loopback receiver. Public `/health` reports whether submissions are enabled: `{"ok":true,"accepting":true}` during the controlled live checks. Setting `SUBMISSIONS_ENABLED=0` and restarting only the receiver closes submissions while retaining reports and the verification page. See [Tunnel prerequisites](https://developers.cloudflare.com/tunnel/get-started/) and [Universal SSL coverage](https://developers.cloudflare.com/ssl/edge-certificates/universal-ssl/limitations/).

The deployment uses two dedicated unprivileged systemd services: a receiver on `127.0.0.1:3210` and an outbound-only `cloudflared` connector pointing directly to it. The connector's metrics stay on `127.0.0.1:3211`. Existing Docker containers, firewall, Tailscale, and reserved listeners are preserved. Cloudflared uses ephemeral UDP sockets for outbound QUIC connections. Root owns the portable runtimes and code; only the receiver's private state directory is writable. A shared resource slice caps combined CPU at half a core and memory at 256 MiB, with individual service caps and no swap expansion. Feedback logs use a separate bounded journal namespace. The installed runtimes are Node 24.22.0 and cloudflared 2026.10.1, checked against vendor SHA-256 metadata.

Publish only this hostname to `http://127.0.0.1:3210`, with an unmatched-route 404 and no private-network/CIDR routes. `TRUST_PROXY=cloudflare-tunnel` applies to this direct path only. Keep Cloudflare visitor-IP headers intact; do not enable Pseudo IPv4 header overwriting or visitor-IP removal. Edge rate limiting should block excessive requests, without putting a login or JavaScript challenge in front of the JSON API. The hosted `/verify` page supplies the explicit Turnstile check.

The account owner created a tunnel named `waterhole-feedback` and a Managed Turnstile widget named `Water Hole feedback`, restricted to the exact public hostname with pre-clearance disabled. The tunnel token, public site key, and server secret were saved in a private local file outside the repository, then the required secrets were transferred over verified SSH into root-owned server configuration. The deployment uses the dedicated capped service instead of the dashboard's generic privileged service-install command. [Tunnel dashboard setup](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/), [Turnstile widget setup](https://developers.cloudflare.com/turnstile/get-started/widget-management/dashboard/).

Direct-IP HTTPS is now possible with short-lived IP certificates, but would require certificate automation and a new public listener and would expose the shared gateway directly to feedback traffic. It is not the chosen deployment. [Let's Encrypt IP certificates](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability).

## Verification and remaining work

Client tests cover transport validation, drafts, screenshot bounds, keybindings and frame-message validation. Browser checks cover capture/removal, keyboard reporting, rating, developer warp, cancellation and retry. An integration check passes real captured PNGs through the local HTTP service into SQLite and verifies deduplication and survey storage. Only the external human-check provider is mocked in that local integration; native Electron compatibility is not established by it.

Deployment checks on the actual host cover public TLS, no-store responses, 404 for public read/admin routes, allowed `Origin: null` transport, and 503 for both closed submission APIs. The configured verification page remains available while submissions are closed, allowing the live widget to be checked without accepting reports. A private transient service exercised the deployed parsing code with synthetic verification that always rejects: four simultaneous 1600 by 1200 RGBA PNGs of 834,663 bytes each, fifth-request overload rejection, corrupt CRC and decompression-bomb rejection, oversized-body rejection, and unsupported content-type rejection. No provider calls or records were produced. The Windows client sent its inputs through a temporary localhost SSH forward, which was then closed.

With the production 64 MiB V8 heap setting and 128 MiB service cap, that bounded check took 8.8 seconds including network waits and used about 1.4 CPU seconds. The receiver's measured cgroup memory peak was 96.7 MiB, with no hard-limit or OOM events. The combined feedback slice, including the ordinary idle receiver and private test service, peaked at 190.8 MiB under its 256 MiB cap. Process RSS also includes shared pages and is not the same as memory charged to the cgroup. These are small deployment checks, not an attack-capacity guarantee. The private inbox was still empty afterward, and existing VPN services remained active.

The subsequent live reporting check used the real hosted Turnstile widget and the game's verification and transport modules from a browser context with an opaque origin. Managed verification completed automatically and closed its dialog on success. The public API validated the resulting token and stored a clearly labelled development report with a canonicalized 8,903-byte PNG. A separate request with an invalid token returned 403 `verification_failed`, without insertion. A disappearing verification dialog is expected after a successful callback; the receiving page's success or error status determines the result.

Public rate-limit checks reached the receiver's 10-attempt visitor-IP allowance and returned JSON 429 with `Retry-After`. Changing `X-Forwarded-For` did not bypass the limit. Supplying a forged `CF-Connecting-IP` was rejected by Cloudflare before the receiver, with a plaintext 403/error 1000 response. Only the receiver was restarted afterward to clear this controlled test's volatile counters. These checks do not establish the edge rate rule, which is still pending.

Before public launch, configure an edge rate rule that blocks excessive JSON API traffic without challenging the API itself. The free plan permits one rule with path matching and IP counting, a ten-second counting period, and a ten-second mitigation duration. A provisional setting is ten requests per ten seconds across `/api/reports` and `/api/surveys`, followed by a ten-second block. This also counts preflights and other methods; it is separate from the receiver's hourly limits. Free rules cannot match the hostname, so the path rule also applies to those paths on other proxied hosts in the zone. See [Cloudflare rate-limiting availability](https://developers.cloudflare.com/waf/rate-limiting-rules/).

Native testing remains pending: Windows launch was blocked by DeviceGuard, and Mac testing must run on the actual Mac. The widget itself loads on the HTTPS verification page, avoiding direct `file://` widget embedding.
